## 2. 「effective 2B」的实现机制（实测自 config.json）

`enable_moe_block = False`，**不是 MoE**，没有专家稀疏性可省。压缩来自三处：

| 机制 | config 字段 | 效果 |
|---|---|---|
| **PLE**（Per-Layer Embeddings） | `hidden_size_per_layer_input = 256`<br>`vocab_size_per_layer_input = 262144` | 每层用 256 维的低秩输入嵌入，而非 1536 维全量 |
| **KV 共享** | `num_kv_shared_layers = 20` | 35 层中约 20 层复用其他层的 KV，独立 KV 层仅约 43% |
| **混合注意力** | `layer_types`：28 × `sliding_attention`（`sliding_window = 512`）<br>+ 7 × `full_attention`（`global_head_dim = 512`） | 80% 的层 KV 封顶在 512 token，与上下文长度无关 |

其他相关字段：`num_key_value_heads = 1`（**单 KV 头**）、`head_dim = 256`、
`global_head_dim = 512`、`hidden_size = 1536`、`intermediate_size = 6144`、
`use_double_wide_mlp = True`、`tie_word_embeddings = True`、
`max_position_embeddings = 131072`。

> 注：`text_config` 是**逐层异构**的。直接读 `config.text_config.head_dim` 会抛
> `AmbiguousGlobalPerLayerAttributeError`，需经 `per_layer_config[i]` 访问，
> 或在 config 上设 `allow_global_per_layer_attribute_access = True`。

## 3. PLE 的访问模式：适合留在磁盘流式读取

**这是决定端侧内存的关键一项。**

PLE 的用法是**按 token id 取行**（gather），不是按层取列切片：

```
第 L 层、token id = T 的贡献 = embed_tokens_per_layer[T, L*256 : (L+1)*256]
```

在当前 `[262144, 8960]` 布局下，一个 token 的全部 PLE 贡献恰好是**一整行连续的
8960 × 2 = 17.9 KB**。因此：

- ✅ 每 token 只需一次 17.9 KB 的连续闪存读取，对 mmap / 流式加载是最理想的模式
- ✅ **不需要重排张量**。若改成 `[35, 262144, 256]`，每层内部连续，但每 token 的读取
  反而变成 35 次跨步访问——对实际访问模式更差
- ⚠️ prefill 阶段读取量 = `n_tokens × 17.9 KB`，8K 上下文约 143 MB（一次性）

**结论：引擎选型时第一个要验证的能力就是「PLE 能否 mmap/流式加载而不整体驻留」。**
这一项直接决定常驻内存是 ~1.5 GB 还是 ~2.9 GB（见 §5）。

## 4. decode 速度估算模型（已在本机验证）

decode 阶段每生成一个 token 都要把常驻权重完整读一遍，因此是**内存带宽瓶颈**：

```
tok/s ≈ 有效内存带宽 ÷ 每 token 需读字节数
```

**本机 bf16 实测验证**（预热后交替对照 4 轮）：

| 量 | 值 |
|---|---|
| 每 token 需读权重 | 9.51 GiB = 10.21 GB |
| 实测 decode | 17.08 tok/s |
| 反推隐含带宽 | **174.4 GB/s** |
| 线程饱和实测上限 | 185 GB/s |
| 吻合度 | **94%** → 模型成立 |

线程缩放数据（同样证明是带宽瓶颈而非算力瓶颈）：

| threads | 1 | 2 | 4 | 5 | 8 | 12 | 15 |
|---|---|---|---|---|---|---|---|
| tok/s | 7.1 | 10.5 | 14.6 | 15.8 | 16.5 | 16.4 | 18.1 |
| 隐含带宽 GB/s | 72 | 108 | 149 | 162 | 168 | 167 | 185 |

**4–5 线程即饱和**（torch 默认取 5 = 性能核数，已接近最优），拉到 15 线程只多 15%。

prefill 实测（本机 CPU）：约 **30 tok/s**，64/128/256/512 tokens 分别为
32.8 / 33.3 / 33.9 / 40.1 ms per token，近似线性（28 层 sliding attention 抑制了 O(n²)）。

## 5. 手机端估算

每 token 需读 = 常驻权重 1.29 GB（Q4_K_M）+ PLE 行 gather 17.9 KB + KV cache。

| 平台 | 峰值带宽 | 理论 tok/s | **实测量级（×0.65）** |
|---|---|---|---|
| 旗舰 LPDDR5X（8 Gen3 / 天玑9300） | 77 GB/s | 60 | **~39** |
| 中高端 LPDDR5X | 60 GB/s | 46 | **~30** |
| 中端 LPDDR5 | 45 GB/s | 35 | **~23** |
| 上一代 LPDDR5 | 34 GB/s | 26 | **~17** |
| 低端 LPDDR4X | 25 GB/s | 19 | **~13** |

KV cache（int8，已计入 `num_kv_shared_layers = 20`）：

| 上下文 | bf16 全独立 | bf16 共享后 | **int8 共享后** |
|---|---|---|---|
| 2K | 42 MiB | 18 MiB | **9 MiB** |
| 8K | 126 MiB | 54 MiB | **27 MiB** |
| 32K | 462 MiB | 198 MiB | **99 MiB** |
| 128K | 1806 MiB | 774 MiB | **387 MiB** |

**上下文不是内存瓶颈**——8K 只占 27 MiB。这是单 KV 头 + 80% 层 sliding window + KV 共享三者叠加的结果。

> **精算修正**：上表按「独立层比例 (35−20)/35 = 0.43」粗估。在
> [gemma4-reference-spec.md](gemma4-reference-spec.md) §3.6 查明 KV 共享的确切结构后
> （自有 KV 仅层 0–14，共享方只有 layer 13/14，且 layer 13 虽是 sliding 层却需一份额外的
> **全长**副本），精算值为 2K=10 MiB / 8K=**31 MiB** / 32K=115 MiB（int8）。
> 与粗估差约 15%，**结论不变**：上下文远不是瓶颈，权重才是。

### 5.1 自研引擎本机实测（f16，**不是**手机端、**不是** int4）

`third_party/tiny-llm` 已跑通真模型全链路（导出 → 加载 → 前向 → greedy
decode → 在回合结束符正确停止）。以下是**实测值**，与上面的估算分开列，
因为口径不同：这里是 **f16**（8.6 GiB 文件）、在 **Mac 开发机**上、
用 `--matvec-impl neon_mt_kv_nt --ops-impl neon`。

导出产物：`models/tiny/gemma4-e2b-f16.tqwen`
9,257,206,272 字节 / 541 张量 / **4.6286B** 参数（与 config 结构参数数独立吻合）/
max_seq_len 8192 / PLE 行字节 **17920**（= 8960×2，与 §3 记的 17.9 KB 一致）。

**三轮交替对照**（同一 prompt，17 token，生成 40 token；交替先后顺序以消除
热状态偏差 —— 这是 R11 那次假加速教训留下的纪律）：

| 配置 | 常驻权重 | 峰值 RSS | prefill | decode |
|---|---|---|---|---|
| **PLE 留盘** `--ple-ssd` | 4348 MB | **4.54 GiB**（三轮完全一致） | 386 ms → **44.0 tok/s** | 28.06 ms/tok → **35.6 tok/s** |
| PLE 常驻 | 8828 MB | 7.81–8.63 GiB | 490 ms → 34.7 tok/s | 28.90 ms/tok → 34.6 tok/s |

三条结论：

1. **PLE 留盘省 3.3–4.4 GiB 常驻（约 44%），且 decode 不慢反而略快 2.8%、
   prefill 快 21%。** 「留盘会拖慢」这个直觉在这里是反的：少 4.4 GB 常驻
   意味着更小的 cache/TLB 工作集。每 token 只多一次 17.9 KB 的 pread，
   相对 4348 MB 的权重扫描完全可以忽略 —— §3 的预测被实测证实。
2. **decode 确实是带宽墙**：4348 MB × 35.6 tok/s = **154.8 GB/s**，
   而本机线程饱和实测上限是 185 GB/s（§4），即打到 **84%**。
   这说明 kernel 已经接近该机的带宽极限，继续在算子上优化不会有收益；
   要提速只能减少每 token 的字节数（即 int4，见 #23）。
3. **ref 标量 kernel 慢 50 倍**（1564 ms/tok prefill、1780 ms/tok decode）。
   任何性能测量都必须显式指定 `--matvec-impl`/`--ops-impl`，
   默认是 ref。

**KV cache 实测 288.0 MiB @ ctx 8192**，与精算值逐位吻合
（15 个持有槽：12 个 sliding head_dim 256 + 3 个 full head_dim 512，
n_kv_heads=1，fp32，K/V 各一份 = 302.0 MB = 288.0 MiB）。
⚠️ 这比 §4 精算的「8K = 31 MiB」大一个数量级，因为那份精算假设了
**int8 + sliding 层按窗口裁剪存储**，而当前实现是 **fp32 + 全长存储**
（全长是必需的：提供方 layer 13 要给共享层供全长副本，见设计文档 R1）。
两项都可优化：`--kv-f16` 减半（gemma4 前向目前显式拒绝，未验证）、
按窗口裁剪需先解决「位置 → 槽内偏移」的取模映射。
**但即便 288 MiB 也远小于权重的 4348 MB，§4 的结论不变：瓶颈是权重。**

### 5.2 i4 实测（RTN，group_size=64，非对称）

`models/tiny/gemma4-e2b-i4.tqwen`，量化范围 = 全部 2D matmul 权重 + PLE 表；
embed（= tied lm_head）保留 f16；norm 与 layer_scalar 保留 f32。

| 指标 | f16 | **i4** | 变化 |
|---|---|---|---|
| 文件 | 8.6 GiB | **2.96 GiB** | −66% |
| 常驻权重（PLE 留盘） | 4348 MB | **1776 MB** | −59% |
| 峰值 RSS | 4.54 GiB | **2.02 GiB** | −56% |
| PLE 行字节 | 17920 | **5040** | −72% |
| PLE 留盘体积 | 4480 MB | **1260 MB** | −72% |
| KV cache @8K | 288 MiB | 288 MiB | 不变（KV 不量化） |
| 导出耗时 | ~45 s | 51.6 s | — |

**常驻 1776 MB 与设计时估的 ~1.8 GB 吻合**；2.02 GiB 峰值 RSS 对 6 GB 内存的
中端机是可行的（f16 的 4.54 GiB 不可行）。

输出质量抽检正常，且在回合结束符正确停止：

> 问：用一句话解释什么是内存带宽。
> f16：**内存带宽是衡量和系统化量于内存存储或传输的数据量能力的指标。**
> i4 ：**内存带宽是指数据在内存和处理器之间传输的速度，决定了系统处理数据的效率。**

i4 这版措辞反而更顺 —— 但**单条抽检不能用来判断量化优劣**，2B 有效参数的
模型输出本身就有波动；要判断得看 PPL（尚未测，见下方待办）。

⚠️ 首次测量时 i4 的 decode 是 339 ms/token（比 f16 慢 12 倍），
原因是 `--matvec-impl` 只设一个名字而 i4 与 f16 是两个独立注册表，
main.cpp 的 `is_i4` 分支漏设 f16 → tied lm_head 落到标量 ref。
**已修**（tiny-llm `781f5b8`），修完的速度见 §5.3、质量门槛见 §5.4。

另一个陷阱：`sdot5` / `sdot5_mt` **要求对称量化**（zero 恒为 8），
非对称文件用它会退化成单 token 重复且不报错。非对称 i4 要用 `sdot4_mt`。
症状与「量化精度不足」完全一样，隔离方法是把 impl 退回 `ref` 再跑一遍。

### 5.3 i4 的速度（已修，此前测不准）

`--matvec-impl` 只设一个名字，而 i4 与 f16 是**两个独立注册表**；
main.cpp 的 `is_i4` 分支只设了 i4 + f32、**漏设 f16**，于是 tied lm_head
（f16，805 MB，每 decode step 全读一遍）落到标量 ref，约 330 ms/token。
同一段代码里 `vq2` 与 `gptq` 分支都设了 f16，`gptq` 那边甚至写了注释
「漏设 f16 表会让 fp16 lm_head 落到标量 ref（坑 #21 同类陷阱）」——
同一个坑，三个分支各写一遍，只有 i4 漏了。此前漏不出来是因为 i4 文件
只有 Qwen 在用、其 embed 存 f32；gemma4 是第一个 embed 为 f16 的 i4 文件。

修完（tiny-llm `781f5b8`）后 i4 vs f16 **三轮交替对照**：

| | prefill | decode | 峰值 RSS |
|---|---|---|---|
| **i4** | 215.4 ms → **78.9 tok/s** | 19.87 ms/tok → **50.3 tok/s** | **2.02 GiB** |
| f16 | 509.8 ms → 33.3 tok/s | 30.70 ms/tok → 32.6 tok/s | 4.54 GiB |
| 加速 | **2.37×** | **1.55×** | **−56%** |

decode 只快 1.55× 而不是字节比的 2.45×，因为 lm_head（805 MB f16）在两种
格式下**完全相同**，成了共同下界：i4 每 token 读 1776 MB，其中 805 MB
不随量化变。

带宽核算：i4 是 1776 MB × 50.3 = **89.3 GB/s**（本机上限 185 GB/s 的 48%），
明显低于 f16 的 84% —— 说明 i4 已不是纯带宽墙，`sdot4_mt` 的 W4A8
（激活也量化成 int8 走 SDOT）带来额外计算，部分转为 compute-bound。

### 5.4 i4 的质量门槛：**不通过**

语料 = 模型自带 README.md（7450 token 切 7 段 × 1024，计 7161 token）；
参考 = HF 原生 bf16 权重，同一 512 token 前缀，teacher-forcing 逐位置比 argmax。

| 对照 | argmax 一致率 |
|---|---|
| C++ f16 vs HF bf16 | **98.83%**（6/512 不一致） |
| C++ i4 vs HF bf16 | **76.37%**（121/512 不一致） |
| C++ f16 vs C++ i4 | 76.17% |

f16 侧 98.83% 说明**实现本身基本精确**，那 22 个百分点全部来自
RTN(group_size=64) 的量化损失。已排除两种假阴性解释：margin(top1−top2)
中位 5.76（不是低 margin 平票）、|logit|max ≥29.9 的位置只有 8–11/512
（不是 softcapping 饱和压平）。

**PPL 这一项本次测量无效，不能用**：

| | ppl_nll | ppl |
|---|---|---|
| f16 | 4.663950 | 106.054 |
| i4 | 4.408743 | **82.166** |

i4 反而「低 22.5%」。这是**归谬**而非好消息：argmax 一致率只有 76% 的模型
不可能真比 98.8% 的困惑度低 22%。原因是语料选错 —— README（含大量 markdown）
PPL 高达 106，模型根本没在预测这段文本，target token 极少落在 top 附近，
于是 NLL 由整体 logit 尺度主导而非排序；加上 softcapping 压平差异，
一个挪动整体分布的量化扰动可以降低 NLL 而不改善任何排序。

> **PPL 只有在「模型确实能预测该语料」（PPL 量级个位数到几十）时才是有效门槛。**
> 这与 KNOWN_ISSUES R11（那个假的 3.1× 加速）同一类：**测量口径无效时，
> 数字越漂亮越危险。** 本次差点把「i4 的 PPL 更好」写成结论。
> 另注：单段语料（1023 token）上 f16 67.413 / i4 67.866（+0.67%），
> 与全语料的反向结果不一致 —— 这个不一致本身也是口径不稳的佐证。

### 5.5 四组消融：RTN 不可用，且不是调参能解决的

`tools/eval_i4_quality.py`，534 token teacher-forcing，参考 = HF 原生 bf16。
语料由 f16 模型 greedy 生成（**启用真 EOS**，见下方语料坑）。

| 变体 | argmax 一致率 | 相对 f16 |
|---|---|---|
| f16（基线） | **97.57%** | — |
| i4 gs=64, W4A8 (`sdot4_mt`) | 60.11% | −37.5 |
| i4 gs=64, W4A32 (`neon_mt`) | 61.99% | −35.6 |
| i4 gs=64, 标量 `ref` | **61.99%** | −35.6 |
| i4 gs=32, W4A32 | 63.86% | −33.7 |
| i4 gs=64 但 PLE 保 f16 | 60.67% | −36.9 |

四组消融互相独立地排除了所有次要因素：

1. **kernel / 激活量化不是主因**：W4A32 与标量 ref 结果**完全相同**（61.99%），
   说明 `sdot` 系的 W4A8（激活也量化成 int8）只贡献 1.9 个点。
2. **group_size 影响很弱**：64→32 只换来 +1.87 点，而体积 +8.5%。
3. **PLE 表不是主因**：PLE 占参数量 **51%** 且以乘法门控进入全部 35 层，
   原本是头号嫌疑；实测保 f16 只回收 +0.56 点。这个实验是**免费的** ——
   PLE 本来就留盘，保 f16 不增加任何常驻内存，只把磁盘从 2.96 抬到 6.11 GiB，
   所以它的阴性结果很干净。（为此给 exporter 加了 `--ple-dtype`；
   注意 V4Ext 的 `ple_row_bytes` 必须按 PLE **自己的** dtype 算：
   i4/gs64 是 5040、f16 是 17920，差 3.56 倍，用错就是静默乱码。）
4. **裁剪量化 range 反而更差**：clip 分位 0%→9.45%、0.1%→9.36%、
   1%→10.84%、2%→13.83%、5%→21.46%（相对 L2）。
   ⚠️ 这条的**结论对、依据不充分**：百分位裁剪是个粗糙代理（它砍掉真实极值），
   不能代表 HQQ 的搜索空间。HQQ 的严格上界见 §5.5.1。

### 5.5.1 HQQ 的理论上界：8.504%，最多再赚 ~1.4 个一致率点

HQQ 优化的是每组的 `(scale, zero)` 两个标量（用半 quadratic 分裂迭代求解，
目标函数与 RTN 同为 `||W − dequant(quant(W))||²`）。故对该空间做网格搜索
即得 HQQ 的**全局最优下界**（layers.0.mlp.gate_proj 前 64 行 = 1536 个组，gs=64）：

| | 相对 L2 误差 |
|---|---|
| 朴素 min-max RTN（现状） | 9.568% |
| **(scale, zero) 全局最优 = HQQ 天花板** | **8.504%** |

最优 clip 比例中位 **0.960**（只比 min-max 窄 4%）。即 **RTN 已经落在 HQQ
搜索空间的 89% 处**，HQQ 最多再降 11% 的权重误差。

换算成一致率：以 group_size 那个数据点为锚（64→32 把误差从 9.61% 降到
8.19%，即 −14.8%，换来 +1.87 点），HQQ 的 −11.1% 约值 **+1.4 点**，
即 62% → **约 63.4%**。离 95% 门槛差得远。

**为什么 RTN 在这个模型上已近最优**：单位高斯的 16 级最优均匀量化器
MSE/σ² ≈ 0.009497（Max 1960）→ 相对 RMS ≈ **9.75%**；均匀分布的对应值是
**6.25%**。实测全局最优 8.504% 落在两者之间 ⇒ 这些权重是**轻尾、亚高斯**的，
min-max 恰好是轻尾分布的近优解，没有离群值可救。

**HQQ 与 GPTQ 优化的不是同一个目标**（这是整件事的核心）：

| | 目标 | 4-bit 下的下界 |
|---|---|---|
| RTN / HQQ | 逐权重重建误差 `\|\|W − Ŵ\|\|` | **~8.5%，硬下界**（16 级均匀量化装不下更多信息） |
| GPTQ / AWQ | 输出误差 `\|\|WX − ŴX\|\|` | 可到 1~2% |

GPTQ 的手段是把已量化列的误差**摊到同行尚未量化的列**（用 Hessian 逆补偿）。
它**不降低单权重误差**（仍是 ~9%），但让**乘积**的误差大幅下降。
35 层 × 3 个残差子块的复利放大的是输出误差，只有直接优化输出误差的方法能挡住。

⇒ **HQQ 不是可选路径，#28（GPTQ/AWQ 类误差补偿）是 i4 可用的必要条件。**
记下这个上界，免得后续再去试 HQQ。

### 5.5.2 PTQ 4-bit 的经验天花板 = 64.42%（实测，非推测）

线索来自 ModelScope 上 `cyankiwi/gemma-4-E2B-it-AWQ-INT4` 的 ignore 列表
（该仓库名字叫 AWQ，实际 `quant_method` 是 **compressed-tensors**，
gs=32 / 非对称 / observer=mse）：320 条 ignore 里与文本塔相关的恰好是
**全部 35 层的 `per_layer_input_gate` 与 `per_layer_projection`**（70 个 Linear）。
而 #27 的消融只测过 PLE **表**保 f16，没测过这 70 个投影层 —— 是唯一未排除的
敏感度来源。它们每个仅 256×1536，70 个合计 27M = 全模型的 **0.6%**。

实测（534 token teacher-forcing，参考 HF bf16，f16 基线 97.57%）：

| 变体 | argmax 一致率 | 文件 |
|---|---|---|
| i4 全量化 gs=64 | 60.11% | 2.96 GiB |
| + PLE 投影层保 f16 | **63.48%** | 3.00 GiB（**+1.4%**） |
| + 再叠 gs=32 + PLE 表 f16 + W4A32 kernel | **64.42%** | **6.25 GiB** |
| f16（基线） | 97.57% | 8.6 GiB |

两条结论：

1. **PLE 投影层是单位参数最敏感的**：+3.37 点只花 +1.4% 体积，
   比 group_size 减半（+1.87 点 / +8.5%）和 PLE 表保 f16（+0.56 点 /
   磁盘 +3.2 GiB）都划算。社区的 ignore 列表是有信息量的。
2. **增益不可加**：四个旋钮单独增益之和约 +7.7 点（预估 67.8%），
   实测只有 +4.3 点（64.42%）⇒ 它们修的是同一份底层误差的不同侧面。
   所以「再找几个敏感层排除掉」收益递减，**不存在靠堆排除项逼近 95% 的可能**。
   而 64.42% 要付 6.25 GiB（已接近 f16 的 8.6 GiB），性价比崩塌。

⇒ **PTQ 4-bit 对 gemma4 不可能达标，64.42% 是实测上限。**
与 §5.5.1 的理论上界互相印证：`(scale,zero)` 搜索空间的全局最优是 8.504%
相对 L2，而 min-max RTN 已达 9.568%（该空间的 89%），所以任何只在
scale/zero/分组粒度/排除项上做文章的 PTQ 变体都撞同一堵墙。
必须换算法档次：**QAT** 或 **GPTQ/AWQ 类输出误差补偿**。

### 5.5.3 ModelScope 上现成产物的可用性排查

| 仓库 | 下载 | 判定 |
|---|---|---|
| **`google/gemma-4-E2B-it-qat-q4_0-gguf`** | 1021 | **最有希望**。Google 官方 QAT（训练时把量化放进回路，模型本身适应量化，不是事后逼近），3194 MiB。但是 GGUF，需写读取器（q4_0 布局简单：每 32 元素一个 scale、对称） |
| `unsloth/gemma-4-E2B-it-qat-mobile-GGUF` | 224 | 同上，且是**专为移动端**的 QAT 变体，与本项目目标最贴合 |
| `cyankiwi/gemma-4-E2B-it-AWQ-INT4` | 59 | 不建议。名字是 AWQ 实为 `compressed-tensors`，runtime 无对应 dtype 需转格式；`observer=mse` 的天花板就是 §5.5.1 算出的 8.504%，大概率同样不达标；README 0 字节、作者未公布任何质量数字 |
| `AXERA-TECH/gemma-4-E2B-it-GPTQ-INT4` | 20 | **名字骗人**：不是标准 GPTQ checkpoint，是爱芯元智 NPU 私有 `.axmodel`（还带 audio/vision 的 axmodel）。用不了。但其布局独立印证了我们的设计：PLE 表以 `.npy` f16 单独存（4480 MiB 未量化）、embed 以 bf16 单独存（768 MiB 未量化），只把文本层压成 419 MiB |

⇒ **下一步应评估官方 QAT GGUF**，而不是自己实现 GPTQ/AWQ：
QAT 的质量上限高于任何 PTQ，且是官方产物、无需校准语料与 Hessian。
代价是要写 GGUF 读取器（q4_0 只需处理「每 32 元素一个 fp16 scale + 对称 int4」）。

**根因**：真权重的重建相对 L2 误差 gs=64 是 9.11~9.86%、gs=32 是 7.90~8.39%、
gs=128 是 10.63~10.91%（layers.0/17/34 的 gate_proj、q_proj、
per_layer_input_gate 全都一样）。朴素 min-max RTN 的理论值：高斯分布
16 级均匀量化，range≈6σ → step=0.4σ → 误差 RMS = step/√12 ≈ **0.115σ**。
观测 9.5%，吻合。**所以这是 4-bit 均匀量化的固有水平，不是实现 bug**
（格式已由 `verify_i4_roundtrip.py` 证明逐位一致，5.96e-08）。

35 层 × 每层 3 个残差子块的复利下，9.5% 的逐权重误差放大成 37 个点的
argmax 损失 —— 这也解释了为什么 group_size 这种二阶手段没用。

**要降到可用的 1~2% 必须有误差补偿**：GPTQ（把量化误差摊到同行剩余权重）
或 AWQ（按显著性缩放通道）。两者都需要校准数据 + Hessian/显著性统计，
本仓没有实现。这是端侧 i4 的真正前置工作，不是调参能绕过的。

### 5.6 PPL 对 gemma4 不是有效门槛（两次独立复现）

先用 HF 校准了 C++ 的 `--ppl`（不做这步就不知道信不信得过）：

| | ppl_nll | ppl |
|---|---|---|
| HF bf16 | 6.15076 | 469.075 |
| C++ f16 | 6.17349 | 479.860 |

相对差 **0.37%**，即 f16/bf16 存储精度差 —— **C++ 的 `--ppl` 是对的**。

但它作为量化门槛失效，两条独立证据：

1. **softcapping 让 NLL 可以被「收窄分布」而非「改善排序」降低。**
   logits 被 tanh 压进 [−30,30]（实测 min=−30.00 已触底、max=25.88、
   log Z 中位 10.25）。实测 gs=32 的 PPL 是 **180.0**、比 f16 的 479.9
   **低 62%**，而它的 argmax 一致率只有 63.86%。排序明显更差的模型
   PPL 反而"更好"，这是归谬。
2. §5.4 用 README 语料时 i4 的 PPL 也比 f16 低 22.5%（一致率 76%）。
   **换了语料、换了 group_size，同一个假象重复出现** —— 说明是口径问题
   而不是语料偶然。

> **对 gemma4 只用 argmax 一致率作量化门槛，PPL 仅参考。**
> 这与 R11（假的 3.1× 加速）同类：测量口径无效时，数字越漂亮越危险。
> 本次连续两轮差点把「i4 的 PPL 更好」写成结论。

**语料构造的坑**：第一版用 `--eos -1` 生成固定 512 token，答案在约 100 token
处就写完了，后 **39%（198/512）全是 `<turn|>` 重复**。这样的语料上 PPL 由
「多确信地预测 `<turn|>`」主导，是 softcap 饱和行为而非语言建模质量。
改为启用真 EOS + 多 prompt 拼接 + 尾部退化截断后：534 token / 274 个唯一
（退化版是 512 token 里只有 194 个唯一）。

### 5.7 端侧可行性的当前判断

**f16 版本现在就是可用的**：常驻 4348 MB + PLE 留盘、峰值 RSS 4.54 GiB、
decode 32.6 tok/s、与 HF bf16 的 argmax 一致率 97.57%。
但 4.54 GiB 对手机偏大（8 GB 机型的 LMK 下风险高）。

**RTN i4 版本内存达标（2.02 GiB）但质量不达标（60.11%）** —— 见 §5.8，
已用官方 QAT 解决。

> ⚠️ 本节原来写的结论是「端侧上线目前卡在量化算法，不卡在引擎」。
> **该结论已被 §5.8 推翻**：换用官方 QAT 后一致率到 97.75%，
> 质量不再是阻塞项。当时的推理没错（PTQ 4-bit 的天花板确实是 64.42%），
> 错的是隐含假设「只能自己做 PTQ」—— 官方 QAT 产物一直在 ModelScope 上。

### 5.8 官方 QAT 解决了质量问题（#28 已完成）

放弃自研 GPTQ/AWQ，改用官方 **`google/gemma-4-E2B-it-qat-q4_0-gguf`**
（3194.3 MiB GGUF），转码成 .tqwen。完整依据、格式陷阱与全部实测见
`docs/gemma4-qat-gguf-inventory.md`（尤其 §5 的 nibble 重排、§8 的结果）。

**这是转码而不是重新量化**：Q4_0 的 scale 是 QAT 训练出来的，
先 dequantize 再重量化会把它丢掉。Q4_0 → 我们的 i4 是逐块字节重排
（group_size=32、zero 恒 8.0 ⇒ **对称**，顺带解锁 `sdot5_mt`）；
Q6_K → f16（有损但严格限于 1 ULP，见 inventory §5.1 ①bis）。

| | RTN i4（旧） | **QAT i4（新）** | f16 |
|---|---|---|---|
| 文件 | 2.96 GiB | 6.24 GiB | 8.6 GiB |
| 常驻权重 | 1776 MB | **1906 MB** | 4348 MB |
| 峰值 RSS | 2.02 GiB | **1.89 GiB** | 4.54 GiB |
| PLE 留盘 | 1260 MB | 4480 MB（f16） | 4480 MB |
| group_size | 64 | **32**（Q4_0 定死） | — |
| **argmax 一致率** | 60.11% | **96.07%**（`sdot6_mt`，W4A8 分组激活 scale）<br>97.75%（`neon_mt`，W4A32 精确参考） | 97.57% |
| decode（最佳内核） | 49.1 tok/s | **49.0 tok/s**（`sdot6_mt`，**96.07%**） | 32.6 tok/s |

常驻 +7.3% 的两处来源都可解释：group_size 64→32 使 i4 从 4.5 bpw 变
5.0 bpw（+108 MB）；`per_layer_model_projection` 官方保 F16（+20 MB）。
磁盘从 2.96 涨到 6.24 GiB 是因为 PLE 保 f16（Q6_K→i4 的再量化会毁掉
QAT 的 scale，是净损失）；**PLE 留盘流式，不影响常驻内存**。

**质量口径必须换。** 参考不再是原始 HF，而是
`tools/materialize_qat_hf.py` 造的「QAT 权重 bf16 HF checkpoint」。
决定性对照：把**原始 f16 模型**拿去和这个 QAT 参考比，只有 **65.92%** ——
而那是转换零误差的情况（HF 直接前向，没有我们的引擎参与）。
⇒ 「vs 原始模型的一致率」对 QAT **物理上不可能到 95%**，
它量的是 QAT 4-bit 权重与原模型之差，不是转换质量。
（同一份 534-token 语料上，本次对照**精确复现**了 f16=97.57%、
rtn-i4=60.11% 两个旧数字，证明口径可比。）

**W4A8 的激活量化曾是新瓶颈，已修掉。** RTN 时代 W4A8 与 W4A32 只差 1.9 点，
QAT 下差 8.8 点 —— 因为权重误差已被 QAT 压到近零，激活的 int8 量化
反而成了主误差源。根因是 `sdot5` 对**整条激活向量只用一个 int8 scale**，
而 gemma4 的激活有强 outlier 通道（实测 outlier 比 10~12）。

新增 `sdot6`（分组激活 scale，与权重 group_size 对齐）后：
**88.95% → 96.07%，越过 95% 门槛，速度代价在噪声内（49.4 → 49.0 tok/s）**。
且 `sdot6_mt` 的 greedy 序列与 W4A32 精确参考 **md5 完全相同**。
分组量化的收益事先用 `tools/probe_activation_int8.py` 在真实前向上量过：
点积层面误差 4.627% → 0.929%（**4.98×**），重灾区正是 in_dim 最大的
`mlp.down_proj`（6.36% → 1.01%）。详见 inventory §8.5。

⇒ **i4 现在在质量与速度上同时优于 f16**（96.07%@49.0 vs 97.57%@32.6），
而常驻内存只有 1906 MB（f16 是 4348 MB）、RSS 1.89 GiB（f16 是 4.54 GiB）。

**宽语料复测（2152 token / 8 条 prompt，含中英文、数学、代码、翻译）结论加强**：

| | 参考 | 一致率 | 与本语料地板的差 |
|---|---|---|---|
| f16（原始） | HF-原始 bf16 | **98.37%** ← 地板 | — |
| rtn-i4 | HF-原始 bf16 | 76.30% | **−22.07 点** |
| **qat-`sdot6_mt`** | HF-QAT bf16 | **97.82%** | **−0.55 点** |

**量化损失从 22.07 点降到 0.55 点（小 40 倍）**，已落在 bf16/f16 存储精度差的量级里。
详见 inventory §8.6。

⚠️ 但这证明的是「**量化不再损失质量**」，不是「**质量有保证**」——
一致率量的是引擎对 Google QAT 模型的复现保真度，不是该模型在任务上有多好。
任务级准确率、长上下文、多轮、非 greedy 采样、真机，以及「QAT 模型本身好不好」
（80.16% 的漂移量说明它相对原模型改动很大）**全部未测**。见 inventory §8.6 末尾。

另一条方法论：**地板值本身随语料变**（README 98.83%、窄语料 97.57%、
宽语料 98.37%），任何一致率数字都必须与同一份语料上现测的地板比，
不能跨语料引用常数。

（附带一条判据上的教训：88.95% 在文本上其实看不出劣化 —— 两个内核输出
语义完全相同，差别只在 markdown 加粗范围和一个「它」字。argmax 一致率会
系统性过度惩罚格式层面的近平局，别把它当唯一判据。）

**即：端侧上线不再卡在量化算法，也不再需要在速度与质量之间取舍** ——
`sdot6_mt` 同时给出 96.07% 与 49.0 tok/s。剩下的只有 inventory §9 的遗留项
（W4A32 内核未优化，现仅剩「需要精确参考」这一个用途；unsloth UD-Q4_K_XL 未试）
与 #24 的 Android 真机实测。引擎侧（格式、导出、绑定、前向、KV 共享、
sliding window、PLE 流式、Android 交叉编译）此前已全部打通并验证。

> **这些数字不能直接当手机端结论用。** 手机端的估算（§5 表格）针对
> Q4_K_M / 2.61 GB 磁盘 / 1.29 GB 常驻，而这里是 f16 / 8.6 GiB / 4.35 GB。
> 本机实测的价值是：① 证明 PLE 流式机制在真模型上成立且不掉速；
> ② 证明 decode 已到带宽墙，故 int4 是唯一有效的提速方向；
> ③ 给出一个可复现的开发机基线。手机端仍需 #24 实测。

## 6. 估算的不确定性（必须连同数字一起看）

1. **×0.65 的降额系数是假设值**，非实测。真实 CPU 推理通常落在峰值带宽的 50–80%
2. **带宽模型假设 int4 反量化零开销**。ARM CPU 若缺少 int4 点积指令，反量化的计算成本
   可能反超带宽成为瓶颈，实际速度会明显低于上表——**这是最大的风险项**
3. **若引擎走 NPU/GPU 而非 CPU，上表全部作废**。NPU 通常有原生 int4/int8 通路可能更快，
   但也可能因算子覆盖不全而回退 CPU
4. 常驻 RAM 中「运行时开销 0.15–0.30 GB」为经验估值，未实测
5. 未计入 Android 的 per-process 内存限制与 LMK（low memory killer）行为；
   1.5 GB 常驻的 native 分配是否会被系统回收，需在目标机型上验证

**所有手机端数字都需在目标机型上实测确认后才可用于决策。**

## 8. 自研引擎（tiny-llm）已验证项

这张清单原本是给「选第三方引擎」用的。现在走的是自研路线
（`third_party/tiny-llm`，分支 `feat/gemma4-ple`），逐项状态如下。
**判据写在每一项后面** —— 「已验证」必须说明是在什么条件下验证的，
否则和没验证一样（本文档 §6 的教训：估算值必须与实测值分开标注）。

### 8.1 真模型尚未导出（当前最大缺口）

上面所有 ✅ 都是在**缩小版假模型**上得到的：6 层 / hidden 64 /
head_dim 32+64 / vocab 512 / ple_dim 16。真模型是 35 层 / hidden 1536 /
head_dim 256+512 / vocab 262144 / ple_dim 256。

导出器目前把全部张量以 fp32 驻留，真模型峰值约 **20.5 GB**（仅 PLE 表
就 9.4 GB），而本机空闲约 18.7 GB —— 强行跑会换页，且波及同机其他服务，
故**没有**导出。需要先把 `write_tqwen` 改成两遍流式（第一遍只读
safetensors 元数据算 offset，第二遍逐张量载入→转换→写出→释放），
峰值可降到单个张量。这是任务 #21，也是 #22（真模型导出 + 常驻内存实测）
和 #23（i4）的共同前置项。

**已经用真 config 算过（不是跑过）的部分**：kernel 的硬编码上限全部通过
（导出期新增校验，见 `validate_runtime_limits`）——

| 常量 | 上限 | 真模型实际值 |
|---|---|---|
| `kMaxHalf`（rope_ref / rope_neon） | 256 | sliding head_dim 256 → half **128** ✅ |
| `kMaxAngles`（proportional_rope_ref） | 512 | 0.25×512//2 = **64** ✅ |
| `kMaxTensorName` | 64 | 最长 **48**（`model.layers.34.post_per_layer_input_norm.weight`）✅ |
| `kMaxInDim`（matvec_i4_sdot*） | 16384 | 加倍宽 intermediate **12288** ✅ |

即：真模型的**形状**不会撞上任何硬编码上限；未验证的是真形状下的
**数值**与**内存/速度**。
